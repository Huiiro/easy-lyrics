# Lyric Timeline v1.0 开发路线图

本文把产品计划转换为可执行排期。基线按 **1 名全职开发者、8 周（40 个工作日）** 估算；如为业余开发，建议按每周 15 小时换算为约 14～16 周。每阶段都产出可独立运行和验收的版本。

## 1. 交付策略

开发顺序保持为“数据 → 行为 → Timeline → 视觉”。首要验证指标不是功能数量，而是能否用 v0.1 从头到尾完成一首歌。实际打完 3 首不同语言和节奏的歌曲后，才冻结打轴交互并扩大 Timeline 投入。

每个阶段必须同时满足：

1. 功能验收通过；
2. `typecheck`、`lint`、单元测试、生产构建通过；
3. 新增核心逻辑有测试，用户数据格式有版本号；
4. 已知问题记录清楚，无阻塞下阶段的数据结构缺陷。

## 2. 周期与里程碑

| 周期           | 阶段与版本       | 主要交付                                                 | 阶段出口                                            |
| -------------- | ---------------- | -------------------------------------------------------- | --------------------------------------------------- |
| 第 1 周前 2 天 | Phase 0 / v0.0.1 | Electron + Vue + TS + Pinia；IPC；规范；CI 基线          | `npm run dev` 显示主窗口，IPC ping 成功             |
| 第 1 周后 3 天 | Phase 1          | Project 模型；音频导入；播放、暂停、Seek、音量、倍速     | MP3/WAV/FLAC 至少各验证 1 个样本；时间来自媒体元素  |
| 第 2 周        | Phase 2A         | 歌词导入；三种 Tokenizer；歌词面板；活动 Token           | 中英混合拆分结果可预测，导入可撤销或重新执行        |
| 第 3 周        | Phase 2B / v0.1  | F 打轴；Offset；导航快捷键；Token Inspector              | 完整打完 3 首歌；无丢字、越界或负时间；记录体验反馈 |
| 第 4 周        | Phase 3 / v0.2   | Viewport；刻度；播放头；波形；Token 块；Zoom/Pan         | 5 分钟音频交互流畅；缩放锚点不漂移                  |
| 第 5 周        | Phase 4 / v0.3   | Hit Test；移动/缩放 Token；联动边界；整句移动；吸附      | 拖动只生成一次历史操作；时间不出现非法区间          |
| 第 6 周        | Phase 5 / v0.4   | Command History；保存/打开；脏状态；自动保存；音频重定位 | 强退后可恢复；保存往返结果一致；旧版本报错可理解    |
| 第 7 周        | Phase 6 / v0.5   | JSON、LRC、Enhanced LRC、SRT、TXT；模板预览与预设        | 固定样例做快照测试；所有导出可被目标软件读取        |
| 第 8 周        | Phase 7 / v1.0   | Loop、pre-roll、自动跟随、最近工程、异常处理、性能与发布 | 5 首回归歌曲通过；安装包冒烟测试；无数据丢失级缺陷  |

计划预留约 15% 缓冲，优先消化在第 3、5、6 周的交互和数据可靠性风险。若进度落后，先延后多选、复杂吸附、快捷键 UI 等第四优先级功能，不压缩保存恢复和真实歌曲回归。

## 3. 工作分解与估算

### Phase 0：工程基线（2 天）

- 主进程、preload、renderer 和 shared 分层：0.5 天
- 严格 TypeScript、ESLint、Prettier、Vitest：0.5 天
- IPC 契约、窗口安全默认值、基础 Store：0.5 天
- 构建验证、README、Git 基线：0.5 天

### Phase 1～2：可用 MVP（8 天）

- 音频层和播放器界面：3 天
- 歌词导入与 Tokenizer：2 天
- 活动 Token、打轴状态机、Offset：2 天
- Inspector、快捷键冲突处理、真实歌曲试用：1 天

这里设置第一次产品决策门：根据真实试用结果确认 F 键语义、句尾结束规则、空白/标点保留策略和英文 Token 规则。未确认前不冻结 Timeline 数据接口。

### Phase 3～4：Timeline（10 天）

- Viewport、刻度、播放头和基本交互：2 天
- 波形解码、峰值缓存与渲染：2 天
- Token 绘制、Hit Test 与选择：2 天
- Move、Resize、联动边界、整句移动：3 天
- 吸附、微调和性能回归：1 天

### Phase 5：数据可靠性（5 天）

- Command 与历史栈：2 天
- `.lyricproj` 序列化、校验与迁移入口：1 天
- 保存、自动保存、恢复和音频重定位：2 天

### Phase 6：导出（5 天）

- 内置格式与时间格式化：2 天
- 简单模板解析器与预设：2 天
- 预览、错误处理和兼容性测试：1 天

### Phase 7：发布（5 天）

- Loop、pre-roll、自动跟随：1.5 天
- 最近工程与异常恢复：1 天
- 性能、无障碍和视觉打磨：1 天
- 五类歌曲回归、打包、发布说明：1.5 天

## 4. 测试矩阵

| 层级     | 重点                                                                  |
| -------- | --------------------------------------------------------------------- |
| 单元测试 | Tokenizer；时间转换；Viewport 坐标；命令撤销；各 Exporter；工程迁移   |
| 组件测试 | PlayerBar；LyricsPanel；TokenInspector；ExportDialog 的状态与键盘行为 |
| 集成测试 | IPC 文件对话框；保存/打开往返；音频丢失重定位；自动保存恢复           |
| 手工回归 | 中文、英文、中英混合、快节奏、慢歌各 1 首完整工作流                   |
| 性能检查 | 5～10 分钟音频、20,000 peaks、5,000 tokens；播放与拖动无明显掉帧      |

建议把时间相关内部数据统一为秒制 `number`，只在输入输出边界格式化；所有修改必须维持 `start <= end`，相邻联动由 Timing/Command 层保证，界面不能直接散改 Project 数据。

## 5. 主要风险与应对

- **快捷键与输入框冲突**：按键路由区分编辑态和全局态，第 3 周用真实工作流验证。
- **媒体时间精度差异**：以 `HTMLAudioElement.currentTime` 为真值，界面用 `requestAnimationFrame`；先实测再决定是否引入 Web Audio 播放。
- **Timeline 模块膨胀**：Renderer、Viewport、HitTester、Interaction、Selection 分离，Vue 仅负责装配。
- **撤销后补代价高**：从首个拖动编辑开始强制通过 Command 提交，mousemove 只预览。
- **工程数据不可升级**：v1 即保存 `version`，读取走校验和迁移入口，禁止直接信任磁盘 JSON。
- **音频格式支持不一致**：验收以 Electron 当前 Chromium 实际解码能力为准，对不支持格式给出可操作错误。

## 6. 近期开发 Backlog

Phase 0 完成后按以下顺序进入第一周：

1. 完善 `AudioSource` 与文件选择 IPC，使用对象 URL 向播放器加载本地音频；
2. 编写 `AudioPlayer` 服务，以媒体事件和 `requestAnimationFrame` 驱动 Pinia 状态；
3. 实现 `PlayerBar` 和时间格式化单元测试；
4. 补 3 种格式的音频冒烟样本与验收记录；
5. 再进入歌词导入和 Tokenizer，避免同时改动两个核心状态域。

## 7. 完成定义

v1.0 的完成不是“页面都有入口”，而是能够连续完成：新建工程 → 导入音频 → 导入歌词 → 逐字打轴 → Timeline 微调 → 撤销/重做 → 保存/重开 → 导出目标格式。该流程必须在五类回归歌曲上完成，并通过安装包而非仅开发环境验证。
